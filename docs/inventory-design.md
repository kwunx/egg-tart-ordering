# 库存设计

## 1. V1.0 方案

采用：

> 下单时扣减库存 + 待支付取消/超时释放库存。

不采用“支付后才扣库存”。

原因：

如果付款后才扣库存，可能出现多个用户都完成支付，但最后库存不足，需要退款。

V1.0 优先保证：

> 成功创建订单的用户已经获得对应库存。

## 2. 原子更新

普通商品购买 1 个：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = :product_id
AND stock >= 1;
```

影响 1 行：

```text
库存扣减成功
```

影响 0 行：

```text
库存不足
```

## 3. 套餐

套餐本身没有独立库存。

例如：

```text
6个任选
原味 ×2
芝士 ×2
芋泥 ×2
```

实际扣：

```text
原味 -2
芝士 -2
芋泥 -2
```

所有扣减必须属于同一个数据库事务。

## 4. 事务

```text
BEGIN
↓
扣商品A
↓
扣商品B
↓
扣商品C
↓
创建订单
↓
创建订单明细
↓
COMMIT
```

任何一个库存不足：

```text
ROLLBACK
```

前面已经扣减的库存全部恢复。

## 5. 取消订单

```text
pending_payment
↓
cancelled
```

同时：

```text
stock + quantity
```

必须和订单状态变化在同一事务中。

## 6. 支付超时

V1.0 可先实现手动取消。

后续增加定时任务：

```text
扫描 pending_payment
↓
超过支付时限
↓
取消订单
↓
释放库存
```

## 7. 防止重复释放

取消操作必须检查：

```text
当前订单状态 == pending_payment
```

只有第一次取消允许释放库存。

第二次取消不再执行库存恢复。

## 8. 并发示例

库存：

```text
stock = 1
```

A/B 同时下单：

```text
A UPDATE → 影响1行 → 成功
B UPDATE → 影响0行 → 库存不足
```

最终：

```text
stock = 0
成功订单 = 1
```

绝不能：

```text
成功订单 = 2
```
