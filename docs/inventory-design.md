# 库存设计

## 1. V1.0 方案

`products.stock` 表示当前可售库存。V1.0 采用下单扣减、待支付取消或超时后恢复的方案，成功创建订单即取得对应库存。

- 支付成功后不再次扣库存。
- Mock 支付确认失败时保留库存，允许同单重试，直至取消或超时。
- 套餐没有独立库存，实际消耗所选普通商品。
- V1.0 包含自动超时回收，不依赖顾客主动取消。

## 2. 原子扣减

先将整单需求按普通商品 ID 汇总，再按 ID 升序执行条件更新：

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :product_id
  AND product_type = 'single'
  AND is_active = TRUE
  AND stock >= :quantity;
```

`:quantity` 必须为正整数。商品和套餐资格由后端先校验；条件更新防止库存不足及已停用商品继续扣减，必须检查受影响行数。

影响 1 行表示扣减成功；有效商品因库存不足影响 0 行时，整单回滚，返回 HTTP 409、业务码 `40901`。商品不存在、类型错误或停用按商品校验错误处理，不能把所有 0 行结果都当作库存不足。

所有商品扣减、订单、订单明细和支付记录必须位于同一事务中，任何一步失败都全部回滚。

## 3. 套餐份数与扣减快照

请求中套餐 `quantity` 表示购买份数；`selections` 表示每份配方，结构为：

```json
{
  "product_id": 10,
  "quantity": 2,
  "selections": [
    {"product_id": 1, "quantity": 2},
    {"product_id": 2, "quantity": 2},
    {"product_id": 3, "quantity": 2}
  ]
}
```

如果商品 10 是“6 个任选”，上述请求购买 2 份，每份配方合计 6 个，实际分别消耗商品 1、2、3 各 4 个。

校验和归并规则：

- 份数和配方子数量均为正整数，同一配方中子商品 ID 不得重复。
- 子商品必须为套餐允许选择的有效普通商品；配方数量之和必须等于 `combo_quantity`。
- 同商品、同配方的购物车行合并数量；配方按子商品 ID 排序比较，不同配方保留不同行。
- 普通商品数量直接作为库存消耗；套餐子商品消耗为每份子数量乘套餐份数。
- 单品与不同套餐共享普通商品时，整单汇总其总消耗，只按汇总量扣减。
- 套餐金额为服务器套餐单价乘份数，不累加子商品零售价。

每个订单明细保存不可变的 `stock_deductions` JSONB，记录该行实际总消耗；普通商品也使用相同结构：

```json
[
  {"product_id": 1, "quantity": 4},
  {"product_id": 2, "quantity": 4},
  {"product_id": 3, "quantity": 4}
]
```

`selections` 保存每份配方快照，`stock_deductions` 保存已乘份数的实际消耗，恢复时不得再次乘份数。快照必须由服务端生成，不能信任客户端提交的扣减数据。取消只读取实际扣减快照，不读取现行套餐配置、商品价格或重新计算配方。

## 4. 创建订单事务与幂等

客户端为一次结算生成 UUID `client_request_id`，双击和网络重试复用该值。数据库设置 `UNIQUE(user_id, client_request_id)`，并保存标准化业务请求的指纹。数据库事务隔离级别统一使用 `READ COMMITTED`。

```text
校验请求格式并标准化，计算请求指纹，查询已有幂等结果
↓
BEGIN
↓
插入带唯一请求键的订单行（金额 0 仅为事务内占位），裁决并发重复请求
↓
锁定 store_settings(id=1) FOR SHARE 并核验接单中
↓
首次请求：校验当前商品/套餐，读取价格并计算金额
↓
按普通商品 ID 汇总并升序原子扣减库存
↓
填入最终金额，保存订单明细、价格及 stock_deductions 快照
↓
创建唯一的 pending 支付记录
↓
COMMIT
```

订单行和请求键必须在读取当前业务数据、扣库存前于同一事务建立，订单提交前对外不可见。并发相同请求由数据库唯一约束裁决，不能仅用“先查是否存在”去重，也不能等扣完库存才检查请求键。占位金额必须在提交前填入最终金额，任何失败都回滚整单，不允许持久化未完成的占位订单。

- 首次创建成功返回 HTTP 201。
- 同用户同请求键、同内容返回原订单当前状态，HTTP 200，不重新校验当前商品、不重新计价或扣库存。
- 同用户同请求键、不同内容返回 HTTP 409、业务码 `40902`。
- 幂等命中应先于当前商品校验，避免商品后续停用或价格变动阻止原订单重放。
- 创建事务失败时，订单、请求键、支付、明细和库存修改全部回滚；响应丢失但事务已提交时，原请求键可找回原订单。

## 5. 支付、取消与库存恢复

支付、手动取消和自动超时关闭统一使用以下锁顺序，并在取得订单及支付记录锁后重新检查状态：

```text
订单行 → payment 行 → 需要更新的普通商品行（ID 升序）
```

支付成功和确认失败均不更新库存。取消/超时仅允许从 `pending_payment` 关闭，且支付状态必须为 `pending` 或 `failed`。

关闭事务根据所有明细的 `stock_deductions` 按商品 ID 汇总并恢复：

```sql
UPDATE products
SET stock = stock + :quantity
WHERE id = :product_id;
```

恢复操作不得添加 `is_active = TRUE` 条件：历史订单里的商品即使已停用，也必须恢复原扣减量。商品采用停用而非物理删除；若快照对应商品异常缺失，应整笔回滚并记录异常，不能跳过该商品后把订单标记为已关闭。

在同一事务中完成库存恢复、`order.status = cancelled`、`payment.payment_status = closed` 和 `cancel_reason`。关闭之后不得再支付，只有首次状态转换可以恢复库存。

已取消订单重复取消返回 HTTP 200，保留原 `cancel_reason`，不再更新库存；已支付订单取消返回 HTTP 409、业务码 `40903`。详细状态组合见 [订单状态机](order-state-machine.md)。

## 6. 支付超时与自动回收

- 默认 `PAYMENT_TIMEOUT_SECONDS=900`。首次插入订单行占唯一键时取一次 `t=clock_timestamp()`，写入 `created_at=t`、`expires_at=t+PAYMENT_TIMEOUT_SECONDS`；后续库存锁等待、填入最终金额、重放或更改配置均不修改该订单的截止时间。
- 支付和取消在取得必要订单及支付锁后，用 `clock_timestamp()` 取得数据库当前时间，`当前时间 >= expires_at` 即到期。
- 不使用事务开始时刻固定的 `now()` / `CURRENT_TIMESTAMP` 判断锁等待之后是否到期。
- 只有待支付订单参与到期关闭；已支付成功的重放不会因超过截止时间而被改为超时。
- 到期支付请求先在事务中恢复库存并写入 `cancelled / closed / cancel_reason=timeout`，提交成功后才返回 HTTP 409、业务码 `40904`。不得在事务内部抛出业务错误导致关闭和恢复回滚。
- 手动取消时若订单已经到期，同样使用 `cancel_reason=timeout`；未到期使用 `manual`。已取消订单重放保留首次关闭原因。

独立轻量 worker 复用订单关闭业务服务，默认 `ORDER_EXPIRY_SCAN_INTERVAL_SECONDS=30`，worker 启动时立即补扫到期订单。不在每个 Web worker 中各自启动定时器，不引入 Redis 或 Celery。

扫描可按批次取得 `pending_payment` 且到期的候选订单，每单独立事务；处理时仍按统一锁顺序锁定并重查状态和截止时间。多实例、重复扫描和进程重启必须安全；某单失败回滚并记录异常，继续处理其他订单，下一轮可重试失败订单。扫描延迟不延长支付期限，支付接口自行执行到期判断。

## 7. 管理员库存调整

V1.0 只支持普通商品可售库存的原子增减，不提供实物盘点值覆盖。新建普通商品的 `stock=0`，首次补货也必须走库存调整并记录。通用商品编辑接口禁止直接覆盖 `stock`，套餐也不能设置独立库存。

调整请求包含：

- `adjustment_request_id`：UUID，同一次调整的双击或网络重试复用。
- `delta`：非零整数，正值增加可售量，负值减少可售量。
- `reason`：必填调整原因；操作者从管理员认证中取得。

`stock_adjustments` 保存管理员 ID、请求 UUID、请求指纹、商品 ID、delta、调整前后可售量、原因和时间，并设置 `UNIQUE(admin_user_id, adjustment_request_id)`。请求指纹覆盖商品、delta 和原因。

调整流程为“查询已有幂等结果→事务内锁定商品→再次查询幂等结果→校验 `stock + delta >= 0`→更新库存并保存调整记录→提交”。第二次查询防止等待商品锁期间已有相同请求完成；不同商品等竞争场景仍由唯一约束兜底，唯一键竞争失败须回滚当前事务，再读取已提交记录比较指纹并返回结果，不能保留该次库存变更。

调整记录与库存更新在同一事务完成。记录中的前后值必须来自锁定后的商品数据，不能使用旧页面传回的库存。库存不足导致负值时拒绝并回滚，返回 HTTP 409、业务码 `40901`。

同管理员同请求键、同内容返回原调整结果，不能重复应用 delta；不同内容返回 HTTP 409、业务码 `40902`。库存调整只访问需要的商品行，不反向获取订单或支付锁。

## 8. 并发与恢复验收

- 库存为 1 时，不同请求键并发购买，只允许一个订单成功，最终库存为 0。
- 相同请求键并发提交或提交响应丢失后重发，只生成一单、一次扣减；不同内容复用请求键必须冲突。
- 单品与套餐共享商品、多份套餐及多行相同配方，扣减总量和恢复总量必须一致。
- 任一商品库存不足或创建中途异常，订单、支付、明细与所有扣减均回滚。
- 支付、手动取消和超时回收并发，最终只能是已支付且不恢复，或已关闭且只恢复一次。
- 套餐配置变更或商品停用后取消，仍按下单时的 `stock_deductions` 恢复。
- 支付等待锁期间跨越截止时刻，返回过期错误前关闭和恢复已提交。
- worker 重复执行、中断后重启及多实例扫描，不重复释放，不遗漏后续可重试的到期订单。
- 库存调整与下单/取消并发，不能覆盖扣减或恢复；调整响应丢失重发不重复增加库存。

## 9. 暂停接单与库存

首次新单事务占有幂等唯一键后锁定 store_settings 单例行，管理员 UPDATE 同行形成互斥顺序。已暂停则回滚整个新单并返回 40906，不占库存；已存在订单的同键恢复、支付及取消库存恢复不受暂停影响。详见 [V1.0 自取与暂停接单规则](v1-operation-rules.md)。
