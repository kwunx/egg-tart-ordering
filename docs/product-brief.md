# 微信小程序点餐系统 - 产品说明

## 1. 项目定位

本项目是一套面向单个蛋挞摊位的二维码点餐系统。

顾客通过微信扫描二维码进入小程序，浏览蛋挞商品、选择普通商品或套餐、加入购物车、提交订单并完成 Mock 模拟支付；摊主通过管理端查看订单、维护商品和库存、更新订单制作状态。

V1.0 明确定位为**单摊位、轻量级、受控验证点餐流程**的系统，不做多门店、多摊位平台化设计。Mock 支付仅验证业务流程，不扣款、不实际收款；V1.0 仅面向授权测试人员使用微信体验版，不公开营业，不制作或交付实物商品。

### 技术与发布范围

采用前后端分离，三个应用保留在同一仓库，源码、构建产物和部署分别管理：

| 应用 | 技术方案 | V1.0 交付目标 |
|---|---|---|
| `backend` | FastAPI JSON API | 顾客及管理端共用业务后端 |
| `admin-web` | Vue 3 + TypeScript + Vite + Element Plus | 独立管理 SPA，页面路径 `/admin/*`，调用 `/api/v1/admin/*` |
| `customer-app` | uni-app + Vue 3 + TypeScript | 编译并适配微信小程序目标 |

uni-app 的多端编译能力用于保留扩展空间，不代表支付宝、抖音或 H5 的登录、支付已经适配。V1.0 顾客端只构建、上传并进行微信体验版受控测试，不包含正式公开营业或其他顾客端目标；平台扩展需另行设计、开发及验证。

前后端分离不要求跨域：受控部署可通过同域 Nginx 分别转发管理页面及 API。V1.0 使用独立测试数据库、商品库存和后台队列，不连接真实营业数据。具体构建、路由和认证契约见 [系统架构](architecture.md) 与 [API 设计](api-design.md)。

### 受控 Mock 运行边界

- `APP_ENV`、`PAYMENT_MODE` 必填；环境显式配置为 `development/test/staging/production` 之一，V1.0 支付模式仅支持 `mock`。缺失、未知、未实现模式或 `production + mock` 均拒绝启动，改填 `wechat` 不会启用真实支付。运行期间发现不允许的配置时返回 HTTP `503`、业务码 `50301`。
- 顾客必须属于后端 `MOCK_ALLOWED_OPENIDS` 精确白名单才能取得顾客 Token 或访问受保护接口；名单按逗号分隔、trim 去空项并去重，空名单不允许任何顾客参与测试，非名单用户返回 HTTP `403`、业务码 `40301`。已有 Token 每次访问仍校验名单；公开商品和接单状态可读，有效环境的管理员与 worker 不因空名单而停用。
- V1.0 所有订单的 `payment_method=mock`，使用该字段识别模拟订单，不增加 `is_test` 列。顾客端和管理端全程显示“模拟测试、未实际收款、不制作交付”，模拟取餐号不是实物领取凭证。
- 测试可完整走过 `paid → making → ready → completed`，仅验证状态和交互。恢复接单或关闭 Mock 失败注入均不解除测试限制，也不等于获准正式营业。

## 2. 核心目标

1. 顾客能够快速完成自助点餐。
2. 摊主能够快速查看和处理订单。
3. 库存能够在并发下保持正确，避免超卖。
4. 订单、支付、库存状态保持一致。
5. 保留后续接入真实微信支付和扩展业务的空间。
6. 通过完整项目实践掌握需求、设计、开发、测试、部署和上线流程。

## 4. 商品模型

商品分为：

- `single`：普通商品
- `combo`：套餐

示例：

- 原味蛋挞 ¥4
- 芝士蛋挞 ¥5
- 芋泥蛋挞 ¥6
- 6个蛋挞任选 ¥25

套餐不拥有独立库存，套餐中的选择会消耗对应普通商品库存。

套餐数量表示份数，选择配置表示每份内容；不同配置分别成行。例如两份六个任选，每份选择原味、芝士、芋泥各 2 个，三种口味分别消耗 4 个，套餐金额为 ¥50。

## 5. 核心业务原则

- 前端展示价格不是最终价格，后端必须重新读取数据库价格。
- 前端提交的用户身份不能直接作为授权依据。
- 库存扣减必须由数据库原子操作保证并发安全。
- 订单创建、库存处理、订单明细和支付记录必须通过数据库事务保证一致性。
- 历史订单保存商品名称、单价和套餐选择快照，不依赖商品当前数据。
- 订单状态和支付状态分开管理。
- 待支付订单取消或超时后，应释放已经扣减/预占的库存。
- 同一次下单重试只产生一张订单；网络结果未知时先恢复原提交结果。
- 待支付时限默认 15 分钟，V1.0 包含自动超时回收；付款、手动取消与超时处理遵循同一套并发规则。
- Mock 支付失败可在原订单期限内重试，成功不再次扣库存；取消后支付记录关闭，库存只恢复一次。
- 库存恢复依据下单时保存的实际扣减快照，不依赖当前套餐配置。
- 管理员只对当前可售库存做增减，调整去重并记录原因、操作者及前后数量。
- 分类、普通商品和套餐均有完整管理定义；套餐属性和允许成员在同一事务保存。可预先配置停用但存在的普通商品，顾客实际选择的商品及其分类必须均启用。
- 分类停用不改写子商品自身的启用标记，但会阻止相关新购买；历史订单的支付、状态处理和库存恢复仍依据原单及快照。
- 新下单读取分类、商品、价格和套餐配置时，与目录编辑通过同一配置锁协调，订单只能采用完整旧定义或完整新定义，不混用价格、配方和快照。

## 7. 成功标准

顾客端验收目标是在 uni-app 编译的微信小程序中完成：

登录 → 浏览商品 → 购物车 → 提交订单 → Mock 支付 → 查看订单。

管理员端验收目标是在独立管理 SPA 中完成：

登录 → 商品/分类维护 → 测试库存维护 → 查看模拟订单 → 模拟制作中 → 模拟待取餐 → 模拟已取餐。

系统在两个用户并发购买最后库存时，只允许库存充足的一方成功，不产生超卖。

重复下单不会重复占库存；支付与取消竞争不会产生“支付成功且库存已归还”；顾客离开后未付款订单会被自动关闭；套餐配置变更不影响旧订单的库存恢复。管理员身份与顾客身份隔离，管理端登录失效后可重新登录并恢复正常使用。

目录配置保存失败不会留下半套套餐；并发改价、停用分类或改套餐时，新订单使用一致的配置并保持库存正确。错误运行环境不能启用 Mock 下单；非白名单顾客不能参加受保护业务测试，测试订单不会进入真实履约。

以上为 V1.0 验收目标，设计完成不代表功能已实现或测试已通过，也不表示获准正式营业或其他平台已能正常登录或支付。未来营业须另行完成可信真实收款、测试与营业隔离及完整验收；本次不要求提前接入真实支付。

## V1.0 已纳入的现场流程模拟

保留模拟支付成功分配经营日取餐号、`ready` 待取餐状态、管理员暂停/恢复接单。暂停只拒绝首次新下单，不影响既有订单；这些流程仅在受控测试环境验证，不授权制作交付。详见 [V1.0 业务与运行边界规则](v1-operation-rules.md)。
