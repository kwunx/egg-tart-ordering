# 微信小程序点餐系统 - 产品说明

## 1. 项目定位

本项目是一套面向单个蛋挞摊位的二维码点餐系统。

顾客通过微信扫描二维码进入小程序，浏览蛋挞商品、选择普通商品或套餐、加入购物车、提交订单并完成 Mock 模拟支付；摊主通过管理端查看订单、维护商品和库存、更新订单制作状态。

V1.0 明确定位为**单摊位、轻量级、可运行验证点餐流程**的系统，不做多门店、多摊位平台化设计。Mock 支付仅验证业务流程，不扣款、不实际收款；真实收款不属于 V1.0 发布范围。

### 技术与发布范围

采用前后端分离，三个应用保留在同一仓库，源码、构建产物和部署分别管理：

| 应用 | 技术方案 | V1.0 交付目标 |
|---|---|---|
| `backend` | FastAPI JSON API | 顾客及管理端共用业务后端 |
| `admin-web` | Vue 3 + TypeScript + Vite + Element Plus | 独立管理 SPA，页面路径 `/admin/*`，调用 `/api/v1/admin/*` |
| `customer-app` | uni-app + Vue 3 + TypeScript | 编译并适配微信小程序目标 |

uni-app 的多端编译能力用于保留扩展空间，不代表支付宝、抖音或 H5 的登录、支付已经适配。V1.0 只发布微信小程序顾客端，不增加其他顾客端目标；平台扩展需另行设计、开发及验证。

前后端分离不要求跨域：生产环境可通过同域 Nginx 分别转发管理页面及 API。具体构建、路由和认证契约见 [系统架构](architecture.md) 与 [API 设计](api-design.md)。

## 2. 核心目标

1. 顾客能够快速完成自助点餐。
2. 摊主能够快速查看和处理订单。
3. 库存能够在并发下保持正确，避免超卖。
4. 订单、支付、库存状态保持一致。
5. 保留后续接入真实微信支付和扩展业务的空间。
6. 通过完整项目实践掌握需求、设计、开发、测试、部署和上线流程。

## 4. 商品模型

商品分为：

- `single`：普通商品
- `combo`：套餐

示例：

- 原味蛋挞 ¥4
- 芝士蛋挞 ¥5
- 芋泥蛋挞 ¥6
- 6个蛋挞任选 ¥25

套餐不拥有独立库存，套餐中的选择会消耗对应普通商品库存。

套餐数量表示份数，选择配置表示每份内容；不同配置分别成行。例如两份六个任选，每份选择原味、芝士、芋泥各 2 个，三种口味分别消耗 4 个，套餐金额为 ¥50。

## 5. 核心业务原则

- 前端展示价格不是最终价格，后端必须重新读取数据库价格。
- 前端提交的用户身份不能直接作为授权依据。
- 库存扣减必须由数据库原子操作保证并发安全。
- 订单创建、库存处理、订单明细和支付记录必须通过数据库事务保证一致性。
- 历史订单保存商品名称、单价和套餐选择快照，不依赖商品当前数据。
- 订单状态和支付状态分开管理。
- 待支付订单取消或超时后，应释放已经扣减/预占的库存。
- 同一次下单重试只产生一张订单；网络结果未知时先恢复原提交结果。
- 待支付时限默认 15 分钟，V1.0 包含自动超时回收；付款、手动取消与超时处理遵循同一套并发规则。
- Mock 支付失败可在原订单期限内重试，成功不再次扣库存；取消后支付记录关闭，库存只恢复一次。
- 库存恢复依据下单时保存的实际扣减快照，不依赖当前套餐配置。
- 管理员只对当前可售库存做增减，调整去重并记录原因、操作者及前后数量。

- 多门店/多摊位
- 会员
- 手机号登录
- 顾客密码登录
- 积分
- 优惠券
- 拼团
- 配送
- 地址管理
- 复杂 SKU / 多规格
- 营销活动
- 复杂财务报表
- 多角色复杂权限

- 真实支付与实际收款
- 支付宝、抖音、H5 等其他顾客端发布及其认证、支付适配

## 7. 成功标准

顾客端验收目标是在 uni-app 编译的微信小程序中完成：

登录 → 浏览商品 → 购物车 → 提交订单 → Mock 支付 → 查看订单。

管理员端验收目标是在独立管理 SPA 中完成：

登录 → 商品/分类维护 → 库存维护 → 查看订单 → 制作中 → 待取餐 → 已取餐。

系统在两个用户并发购买最后库存时，只允许库存充足的一方成功，不产生超卖。

重复下单不会重复占库存；支付与取消竞争不会产生“支付成功且库存已归还”；顾客离开后未付款订单会被自动关闭；套餐配置变更不影响旧订单的库存恢复。管理员身份与顾客身份隔离，管理端登录失效后可重新登录并恢复正常使用。

以上为 V1.0 验收目标，设计完成不代表功能已实现或测试已通过，也不表示其他平台已能正常登录或支付。
