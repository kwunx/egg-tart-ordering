# 测试计划

本文为待实现、待执行的验证计划，不表示相关功能已经实现或测试已经通过。并发与事务用例必须使用真实 PostgreSQL 和独立连接/事务执行，不能仅靠 Mock 数据库证明锁、唯一约束和原子更新有效。

本次架构调整同样只形成文档计划，尚未执行前端构建、浏览器联调或微信真机测试。验证对象为 `backend/` 的 FastAPI JSON API、`admin-web/` 的独立 Vue 3 管理端和 `customer-app/` 的 uni-app + Vue 3 微信目标；V1.0 不要求 H5、App、支付宝、抖音的登录、支付或发布通过。

除环境拒绝与权限反例外，以下业务测试使用显式 `APP_ENV=development/test/staging`、`PAYMENT_MODE=mock`、已加入后端精确白名单的测试顾客及有效管理员；数据库、商品库存和管理队列与真实营业隔离。所有 `paid/making/ready/completed` 变化都是模拟，禁止制作或交付实物。V1.0 只进行微信上传及体验版受控验收，本文同样不宣称新增测试已运行。

### 9.3 开发代理、受控部署路由与条件性跨域

- 管理端开发服务器将 `/api/v1` 原路径代理到 `http://127.0.0.1:8000`，验证 `/api/v1/admin/auth/login` 及库存调整接口到达正确后端，不多加或遗漏前缀。

## 10. 七组补充验收场景

以下七组是 V1.0 订单、支付与库存规则的重点验收项。所有失败用例除检查 HTTP/业务码外，还要检查数据库中的订单、支付、库存及调整记录，确认不存在部分提交。

### 10.1 下单幂等与断网恢复

| 场景 | 预期 |
|---|---|
| 新 UUID 首次提交合法订单 | HTTP `201`；只创建一个订单、一份支付记录，并扣减一次库存。 |
| 同一用户、相同 `client_request_id`、相同内容串行重试及多连接并发提交 | 后续请求 HTTP `200`，返回同一订单 ID 和其当前状态；只创建一单、扣减一次。服务端锁与唯一约束共同生效。 |
| 同一用户、相同标识，修改商品、份数、配方或备注 | HTTP `409`、`code=40902`；原订单和库存不变。内容改变后使用新 UUID 可按新订单规则提交。 |
| 事务提交成功但响应丢失，随后退出并重新进入小程序 | 本地保留原 UUID 与完整内容；恢复时复用原请求，得到原单，不产生第二单。Token 更新不能使请求标识变化。 |
| 原单创建后商品改价、下架、套餐配方修改；分别在原单已支付和已取消后重放请求 | 返回原单当前状态及原快照，不重新按当前商品价格/有效性校验，也不再次扣库存或支付。 |
| 两个不同用户使用相同 UUID；本地切换用户 | 服务端按用户隔离标识；前端不读取或重发其他用户的待恢复请求，订单归属检查仍生效。 |

额外验证：非法 UUID 被参数校验拒绝；事务创建失败全部回滚，不保留幂等占位，不能留下“幂等已成功但订单不存在”的状态；结果未知时不能修改内容并自动另建订单；请求处理中界面禁用重复提交不能成为服务端去重的唯一保障。

### 10.2 套餐份数、全单汇总与历史恢复

| 场景 | 预期 |
|---|---|
| 六个任选套餐，`quantity=2`，每份原味/芝士/芋泥各 2 个 | 每份选择总数为 6，实际每种消耗 4 个，共 12 个；按套餐单价乘 2 计算小计。 |
| 子商品 ID 重复、数量为零/负数/布尔值/小数、每份总数不等于要求、所选商品不允许 | `quantity` 及选择数量严格校验为正整数；请求被拒绝，不生成订单，不扣库存。 |
| 同一套餐相同配方的子商品输入顺序不同；同套餐不同配方 | 相同配方在购物车合并份数，不同配方独立成行；数量和金额保持正确。 |
| 单品原味 1 个，加套餐 2 份、每份原味 2 个 | 全单原味需求为 5；库存为 4 时整单失败，任何其他商品的扣减一并回滚。 |
| 两个并发订单均包含同一普通商品的单品行和多个套餐行 | 全单按普通商品汇总后扣减，商品按 ID 升序处理；库存不负、不因分行漏算而超卖。 |
| 创建后修改套餐数量、可选商品或停用套餐，然后取消/超时取消原单 | 各明细使用下单时的 `stock_deductions` 真实消耗快照恢复，不能按现有套餐配置反推；每种库存恢复量等于原实际扣减量且只恢复一次。 |

检查 `selections` 历史展示和 `stock_deductions` 均已保存；用多个订单明细共用同一普通商品的案例核对汇总与恢复，不能只测一份套餐。

### 10.3 支付、取消与超时的互斥

所有相关操作遵循锁顺序：订单行 → 支付行 → 普通商品 ID 升序；取得锁后使用数据库 `clock_timestamp()` 重新判断到期时间。

| 场景 | 预期 |
|---|---|
| 未到期订单并发支付与手动取消 | 只能产生 `paid + success` 或 `cancelled + closed` 之一；前者不恢复库存，后者只恢复一次，不允许“已支付但库存已恢复”。 |
| 手动取消、多个超时 worker 同时处理同一到期订单 | 只提交一次取消和恢复，最终 `cancel_reason=timeout`；其余处理读取已终结结果，不重复加库存。 |
| 支付请求在到期前发出，但等待订单锁直到到期后 | 以获得锁后的真实数据库时间判定，关闭订单/支付并恢复库存；不能使用请求开始时间或事务开始时间允许支付。 |
| 到期支付触发取消，然后返回 HTTP `409`、`code=40904` | 错误返回前取消事务已经提交；重新查询为 `cancelled + closed`、原因 `timeout`，库存已恢复。抛出业务错误不能回滚这些变更。 |
| 同一用户重复取消，或支付成功后再次取消 | 重复取消不重复恢复；已支付取消返回非法状态冲突 `40903`，订单和支付成功记录不变。 |
| 含多种商品的两个订单以相反的前端行顺序同时执行终结操作 | 实际商品锁顺序仍按 ID 升序；不能因前端顺序不同产生相互等待的死锁。 |

补充事务故障注入：在更新订单、支付或恢复任一商品库存时失败，必须全部回滚，不留下非法状态组合。

### 10.4 到期回收、停机补扫与跨时段运行

| 场景 | 预期 |
|---|---|
| 默认配置创建订单 | `PAYMENT_TIMEOUT_SECONDS=900`，`expires_at` 为服务器创建时间加 15 分钟；在恰好达到到期时间时按到期处理。 |
| 正常扫描 | `ORDER_EXPIRY_SCAN_INTERVAL_SECONDS=30`；独立 worker 每轮扫描到期待支付订单，逐单事务关闭并释放库存。支付接口在两次扫描之间同样拒绝已到期订单。 |
| worker 停机期间有多个订单到期，随后重新启动 | 启动立即补扫；重新处理已取消/已支付订单无副作用。单个订单处理失败不会使整批已处理订单回滚，应记录失败并在后续扫描重试。 |
| 同时启动多个 worker | 可重复发现同一候选订单，但每单锁后重检确保只关闭/释放一次，无须依赖单实例才能正确运行。 |
| 订单在 23:55 创建，次日 00:10 到期；服务重启或配置修改 | 日期跨越不影响 `expires_at`；已创建订单沿用保存的到期时间，不因重启或新超时配置延长。 |
| 设备时钟分别快/慢 15 分钟，切到后台后超时、离线后恢复 | 创建/详情返回响应时实时 `server_time`，按 `expires_at - server_time` 校准剩余时间后按经过时长递减；回前台/恢复网络重新同步，设备绝对时间不导致提前永久禁用或延长支付资格。归零后刷新仍未到期时恢复计时和按钮，不能只靠倒计时取消。 |
| 创建响应丢失后重放、反复查询详情，期间设备时间改变 | 每次响应刷新 `server_time`，但原订单 `created_at/expires_at` 不变；响应和设备时间变化不重置支付时限，到期裁决仍使用后端锁后的数据库时间。 |

worker 在测试环境可用受控短时限验证，但必须保留一项默认值配置校验；禁止为测试直接改写生产配置。

### 10.5 Mock 支付失败、重试与合法状态组合

| 场景 | 预期 |
|---|---|
| 正常 Mock 支付 | 默认成功，订单与支付在同一事务变为 `paid + success`，不再次扣库存。 |
| 服务端测试配置触发失败 | HTTP `409`、`code=40905`，保持 `pending_payment + failed` 且库存仍被占用；到期前可继续支付或取消。客户端传入成功/失败结果不能决定真实处理结果。 |
| 失败后在到期前重试成功 | 复用原订单和同一条 payment，成功后变为 `paid + success`；不新增支付记录、不二次扣库存。 |
| 成功后重复/并发支付，原单后来进入 making、ready 或 completed；重试时间已超过原 15 分钟支付期限 | 优先识别已支付成功，HTTP `200` 返回当前成功结果；保留首次 `transaction_id`、`paid_at` 和取餐号，不生成新流水，不因原期限已过而取消订单；在这些状态请求取消均拒绝。 |
| 成功事务提交后响应丢失 | 前端显示结果确认中并查询原单，最终展示成功；不会把超时当失败，也不会另建订单。 |
| 失败后到期或手动取消；已取消订单再支付 | 前者关闭为 `cancelled + closed` 并释放一次；再次支付时，超时关闭返回 `40904`，手动关闭返回 `40903`，均保持关闭状态。 |

逐项核验合法组合：`pending_payment + pending/failed`；`paid/making/ready/completed + success`；`cancelled + closed`。订单未取消时 `cancel_reason=NULL`，手动取消为 `manual`，到期取消为 `timeout`。任何其他状态组合均应被业务校验或约束拒绝，V1.0 不产生 `refunded`。

### 10.6 管理员库存调整与审计

| 场景 | 预期 |
|---|---|
| 普通商品初始库存 0，使用独立 UUID、`delta=10`、必填原因补货 | 库存变为 10，写入一条 `stock_adjustments`，含操作人、请求标识、增减量、原因及前后数量；商品编辑接口不能覆盖已有库存。 |
| delta 为布尔值/小数/零，reason 为空、全空白或超过 500 字符，非法 UUID、套餐商品、非管理员调用 | `delta` 严格校验为非零整数，`reason` 为 1 至 500 字符且非全空白；请求被拒绝，不修改库存、不写成功调整记录。 |
| 同一管理员、同一 `adjustment_request_id`、同内容并发提交或断网重试 | 只增减一次、只写一条调整记录，返回原结果；唯一约束为 `(admin_user_id, adjustment_request_id)`。 |
| 原调整标识复用但修改 delta 或 reason | HTTP `409`、`code=40902`，库存不变；新操作使用新标识。不同管理员的标识独立。 |
| 扣减库存的调整与下单/超时恢复并发；扣减会使库存小于 0 | 由数据库原子更新/锁串行保证一致；不足时返回 `40901`，无成功审计记录，最终库存不负且不覆盖其他操作结果。 |
| 库存更新成功后写调整记录失败；提交成功后响应丢失 | 前者整笔事务回滚；后者复用原 UUID 恢复原结果，不再次加减。重放结果的前后库存属于原操作，界面另查最新库存。 |

界面同步验收：未确认结果前保留原调整表单和请求标识、禁用重复提交；恢复结果后刷新库存，新商品不能绕过调整入口直接填写初始库存。

## 11. 执行记录与通过标准

- 开发完成后记录每个用例的环境、输入、并发方式、数据库前后值和实际结果；当前文档不填写虚构的“通过”结论。
- 分别记录后端 API、管理端独立构建/浏览器路由、微信目标编译/真机验证结果；前端编译成功不能替代业务并发与恢复测试。
- 重点检查 HTTP `201/200/409` 和整数业务码 `40901` 库存不足、`40902` 幂等冲突、`40903` 非法状态、`40904` 过期、`40905` Mock 失败、`40906` 暂停接单；新增目录接口同时核对 `400/40001`、`404/40401`、`422`，测试名单核对 `403/40301`，运行配置核对 `503/50301`。
- 除正常 API 测试外，必须覆盖提交成功但响应丢失、等待锁跨越到期点、worker 重启、多实例竞争和历史套餐配置变化后的库存恢复。
- 验收底线：合法状态组合、金额快照和实际扣减快照一致；每个下单意图一单一扣，每笔调整一次增减，取消/超时只释放一次，所有失败事务无部分提交。

## 13. 目录管理与配置一致性

### 13.1 完整定义、可售规则及原子保存

| 场景 | 预期 |
|---|---|
| 管理员 POST 分类，随后 PUT 修改名称、排序、启用状态 | 请求完整包含 `name/sort_order/is_active`；创建 HTTP `201`，更新 HTTP `200`，返回和列表反映保存结果。普通顾客不能写管理接口。 |
| 创建 single，编辑 combo 的数量、价格和允许成员 | single 显式提交 `combo_quantity=null`、`allowed_product_ids=[]`；combo 通过同一商品 POST/PUT 完整提交属性和成员。商品类型创建后不可变，通用编辑不改变库存。 |
| 缺少完整定义字段（含应显式提交的可空字段），携带禁止的 stock/id，或字段类型不符 | HTTP `422`；不产生商品、分类或成员的部分写入。不能把 PUT 当成部分更新。 |
| 配置中重复/不存在/非 single 的成员，或不合法的完整业务定义；更新不存在的目标 | 定义校验失败 HTTP `400`、`code=40001`；目标不存在 HTTP `404`、`code=40401`；原定义保持不变，界面保留输入并回显错误。 |
| 套餐配置引用停用但存在的 single；成员的分类也可能停用 | 管理端可保存配置，标明成员不可售；顾客列表/详情/套餐可选项只提供分类与商品均启用的可售对象，提交失效选择被拒绝，不能因可配置而绕过购买资格。 |
| 停用分类后查询商品、创建订单，再恢复分类；商品自身已有停用标记 | 停用分类不修改各商品 `is_active`，但拒绝其相关新购买；恢复后原本停用的商品仍不可售。已有订单继续支付、制作或按原快照恢复，不依赖当前分类状态。 |
| 更新套餐属性后写入成员时注入异常 | 整个事务回滚，旧价格、数量、启用状态和全部成员同时保留；数据库不留下部分提交，新单不能按半套定义成交。 |
| 普通商品 disable，编辑表单失败或保存响应丢失 | disable 成功 HTTP `200`；结构/业务错误回显且不清空表单；响应未知先刷新列表/读取目标核对，不自动重复新建或显示未经确认的成功。 |

逐一覆盖分类创建/编辑/启停、商品创建/编辑/停用、套餐完整编辑。确认数据库仍为既定 11 表，目录配置没有额外锁表，模拟订单没有新增 `is_test` 列。

### 13.2 新单与目录编辑的并发裁决

使用真实 PostgreSQL 独立连接及可控屏障，明确每个事务已取得的锁后再启动竞争者，不能仅靠不稳定的 sleep 期待竞争发生。新单顺序为：请求唯一键 → `store_settings FOR SHARE` → 检查接单 → 读取完整配置/价格/快照 → 普通商品 ID 升序扣减 → 提交；目录写入顺序为：同一 `store_settings FOR UPDATE` → 所需商品 ID 升序 → 原子定义/成员写入 → 提交。

| 场景 | 预期 |
|---|---|
| 新单先取得共享配置锁，管理员并发改价、改每份数量和成员 | 编辑等待新单提交；新单价格、配方资格、名称/价格快照及实际扣减全部来自旧定义。编辑完成后下一个新单使用新定义。 |
| 管理员先取得排他配置锁并提交完整修改，新单随后取得共享锁 | 新单使用完整新定义；旧配方已不合法时拒绝整单，不能使用新价格搭配旧成员或旧快照。 |
| 新单先持共享锁/管理员先持排他锁，两种顺序并发停用分类或商品 | 前者可按锁内有效旧状态提交；后者的新单必须按已停用的新状态拒绝，库存、订单和 payment 不部分提交。 |
| 两个不同新单同时取得共享配置锁，购买不重叠商品 | 两单可同时读配置并推进，不因配置锁把全部新单串行化；共享同一商品时仍由库存行原子更新裁决。 |
| 多目录编辑同时替换套餐成员，或同一完整修改中途回滚 | 所有目录写入先取排他配置锁串行化；新单只能取得某个完整已提交定义，回滚后继续使用原定义。 |
| 检查分类/商品/套餐创建、更新、disable 的锁轨迹 | 均先 `FOR UPDATE` 配置锁，不先锁商品再取配置锁，不先 `FOR SHARE` 再升级；商品锁按 ID 升序。目录编辑不改 `ordering_enabled/notice` 等营业字段。 |
| 库存 delta、支付取号、取消/超时恢复、making→ready→completed 与目录编辑并发 | 这些业务不取得配置锁，不产生反向锁依赖；保持原订单/支付/取号及商品锁顺序和原快照语义，避免后台配置变更阻断原单恢复。 |
| 新单等待期间接单被暂停，或旧单同 UUID 重放 | 取得共享锁后检查最新接单状态，新单按既定暂停规则拒绝；已有幂等结果优先恢复，不重新读取目录或扣库存。 |
| 预置的 store_settings(id=1) 控制行缺失，分别创建新单或执行目录写入 | 整笔事务回滚并返回通用 HTTP `500`，不能默认接单、无锁读取配置或保留占位/成员/库存变更；`50301` 仅用于环境或支付模式守卫，不用于控制行缺失。 |

## 14. Mock 运行环境、测试身份和履约隔离

| 场景 | 预期 |
|---|---|
| 显式 development/test/staging + mock，分别以 API 和独立 worker 启动 | 允许启动；原 15 分钟、30 秒扫描、启动补扫及多实例处理规则继续生效。源码位置统一为 `backend/app/workers/`。 |
| APP_ENV 或 PAYMENT_MODE 缺失/空/未知；production + mock；任意环境改成尚未实现的 wechat | 启动失败，不提供假成功的支付能力；不能用改模式或关闭 Mock 失败注入绕过。V1.0 唯一支付模式为 mock，环境仅四个明确值。 |
| 启动后在测试中注入不允许的运行配置，再调用受保护业务 | HTTP `503`、`code=50301`，无订单/支付/库存变化；前端显示环境不可用，不降级为模拟成功，不丢弃未知结果请求。 |
| MOCK_ALLOWED_OPENIDS 为空或仅逗号/空白 | 有效环境的管理员及 worker 仍能启动和工作；所有顾客登录和受保护接口被拒绝，不签发顾客 Token，公开商品/接单状态仍可读。 |
| 名单含空白和重复项；提交不在名单、只匹配前缀或大小写不同的 openid | 后端按逗号拆分、trim、去重并精确匹配；仅精确名单顾客可取 Token，其他返回 HTTP `403`/`40301`，不支持前缀/通配或客户端自报身份。 |
| 已发 Token 的顾客从生效名单移除，继续查询原单、支付、取消或下单 | 即使 Token 未过期也返回 `40301`，不执行写操作；重新加入有效名单后按原请求标识恢复。既有订单超时回收不依赖顾客仍在名单。 |
| 查看首页、确认/支付结果、订单卡/详情、取餐号、管理队列，依次模拟制作/待取餐/完成 | 全程显著提示“模拟测试、未实际收款、不制作交付”，按钮写模拟动作；每单 `payment_method=mock`，号码仅用于流程测试，不实际制作或领取实物。 |
| 配置并演练微信体验版与测试后端连接 | 测试数据库、库存、队列及凭据与真实营业隔离，测试不写真实库存或真实履约记录；只授权测试人员，不把体验验收当公开营业发布。 |
| 恢复 ordering_enabled、关闭 Mock 失败注入、获得模拟取餐号 | 测试环境/身份/模拟标识及不交付限制全部仍有效；这些动作不能解锁正式营业，也不能使 production + mock 启动成功。 |

验收仍需真实执行证据。V1.0 通过上述受控测试无需现在接真实支付；未来公开营业须另行实现可信收款、测试/营业隔离及完整履约验证，本轮不将其标记为已完成。
