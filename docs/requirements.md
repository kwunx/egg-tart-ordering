# 微信小程序点餐系统 - 需求说明

## 1. 用户角色

### 1.1 顾客

通过 uni-app 编译的微信小程序进行点餐、Mock 模拟支付和查询历史订单。V1.0 顾客端只交付微信目标的受控体验版，不实际收款、不制作或交付实物。

### 1.2 管理员

通过独立的 Vue 3 管理 SPA 维护商品、分类、套餐、库存并处理订单；页面使用 `/admin/*` 路径，通过 FastAPI 的 `/api/v1/admin/*` JSON API 完成管理操作。

V1.0 只有简单管理员身份，不设计复杂 RBAC。

---

## 2. 顾客需求

### 2.1 微信登录

流程：

`uni.login({ provider: 'weixin' })` → 微信小程序平台的 `wx.login` 能力取得 `code` → `POST /api/v1/auth/login` → 后端调用微信接口换取 `openid` → 查找/创建用户 → 后端签发顾客 Token。

顾客端使用 uni-app + Vue 3 + TypeScript，登录封装只针对 V1.0 微信小程序目标。顾客 Token 沿用 Phase 4 的既有方案选择，不因管理端改为独立 JWT 而增加其他顾客认证方式。

后续请求使用：

```http
Authorization: Bearer <token>
```

小程序不能通过自行提交 `openid` 来证明身份。

V1.0 仅允许后端 `MOCK_ALLOWED_OPENIDS` 白名单中的测试顾客登录。名单为逗号分隔配置，去除各项两端空白并去重后，使用微信接口换取的真实 openid 精确匹配；空集合默认拒绝。签发 Token 前及每次受保护顾客调用都要核验，合法非白名单身份返回 HTTP 403、业务码 `40301`，已签发 Token 不能绕过撤出名单后的限制。公开商品和营业状态可浏览，但不因此允许创建订单或支付。

统一通过 `uni.request` 调用现有顾客 API，在请求中携带 Token。Token 和待恢复的提交信息使用 uni-app storage 能力保存，页面进入及应用回到前台时通过 uni-app 生命周期刷新订单状态。收到 `401` 后清理失效 Token 并重新执行微信登录；同一用户恢复未确认结果的下单时，继续使用已保存的请求 UUID 和原请求，不能因页面重建或重新登录自动创建新单。

uni-app 可以编译多个平台，不等于本项目已完成各平台的身份、请求、存储或支付适配。支付宝、抖音、H5 等顾客端均不纳入 V1.0 发布和验收范围。

### 2.2 商品浏览

顾客可以：

- 查看分类
- 查看商品名称
- 查看价格
- 查看图片
- 查看库存状态
- 查看商品详情

顾客商品列表和详情只提供商品及所属分类均启用的数据，不能通过 `is_active=false` 查询停用商品。套餐选项同样排除商品或所属分类已停用的普通商品，库存为 0 仍可作为售罄状态展示，最终购买由下单事务判断。

### 2.3 普通商品

顾客选择数量后加入购物车。

### 2.4 套餐

套餐有固定数量要求。

例如：

`6个蛋挞任选`

则选择数量必须满足：

`2 + 2 + 2 = 6`

以下均无效：

- 2 + 2 + 3 = 7
- 2 + 2 + 1 = 5

同时必须检查所选普通商品库存。

套餐本身不独立扣库存。

多份购买规则：

- 订单行 `quantity` 表示套餐份数，`selections[].quantity` 表示每份配方中的数量。
- 每份所选数量之和必须等于 `combo_quantity`，子商品 ID 不可重复，数量必须为正整数。
- 同商品、同配方可以合并数量；同套餐的不同配方分别成行。
- 套餐金额 = 套餐单价 × 份数，不累计子商品单价作为套餐价格。
- 普通商品行不包含套餐配方，统一使用空数组 `selections=[]`。

例如购买 2 份 ¥25 的六个任选，每份原味、芝士、芋泥各 2 个：金额为 ¥50，三种普通商品各扣 4 个；若还单买 1 个原味，整单原味共扣 5 个。扣减前将整单需求按普通商品 ID 汇总。

## 3. 下单需求

首次创建订单时，后端必须重新校验：

1. 商品是否存在
2. 商品是否有效
3. 商品类型是否正确
4. 套餐选择是否合法
5. 商品当前价格
6. 当前库存
7. 当前用户身份

前端传来的价格只能作为展示数据，不能作为最终结算依据。已成功创建订单的幂等重放直接返回原单及原快照，不重新按当前价格、上下架或库存校验。

### 3.1 下单事务

创建订单时相关数据库操作必须在一个事务中：

```text
BEGIN
  ↓
建立订单行，使用用户 + 请求标识唯一约束裁决并发，固化创建及截止时间
  ↓
锁定 store_settings(id=1) FOR SHARE，检查是否接单
  ↓
校验商品/套餐
  ↓
读取服务器价格
  ↓
汇总普通商品消耗，按商品 ID 升序原子扣减库存
  ↓
填入订单最终金额，保留初始截止时间
  ↓
创建订单明细
  ↓
创建支付记录
  ↓
COMMIT
```

任一步失败：

```text
ROLLBACK
```

不得出现“库存已经扣了，但订单没有创建”的情况。

订单行在事务内先建立以占用幂等唯一键，临时金额可为 0；首次插入时取一次 `t=clock_timestamp()`，写入 `created_at=t`、`expires_at=t+PAYMENT_TIMEOUT_SECONDS`。后续锁等待、填入最终金额或重放均不重新起算期限；提交前必须填入最终金额、明细和支付记录。任一步失败连同订单行全部回滚，不留下半成品订单。请求结构校验、规范化及既有幂等结果查询在扣库存前完成；并发插入唯一键冲突时，回滚当前事务后读取已提交订单并比较内容指纹。

控制行共享锁在当前分类、商品及套餐配置读取前取得，并保持到提交。后台所有目录编辑在同一行先取独占锁后修改配置，因此下单只能使用完整旧定义或完整新定义，不能拼接不同查询时刻的价格和套餐成员。已有订单的幂等重放不再进入当前目录校验。

### 3.2 创建订单防重复

- 客户端首次提交前生成并保存 `client_request_id`（UUID），双击、请求超时、应用重开后恢复同一次提交均复用该标识及原请求。
- 商品、数量、套餐配置或备注变化后，作为新的提交生成新标识；上一笔结果未知时先恢复其结果，不自动另建订单。
- 服务端对规范化后的商品、数量、配方和备注计算 `request_hash`，不包含实时价格、时间或客户端身份字段。具体规范化算法见 [API 设计](api-design.md)。
- 数据库通过 `UNIQUE(user_id, client_request_id)` 保证并发唯一，不能仅用“先查询再创建”防重复。
- 首次创建返回 HTTP `201`；同标识同内容返回原订单当前状态及 HTTP `200`，不重复扣库存、不重置支付期限；同标识不同内容返回 HTTP `409`。
- 失败并完整回滚的创建不保留订单或请求标识占位；没有成功提交结果时，可用原标识重新尝试。

### 3.3 配置变更与新下单的先后关系

- 目录写操作涵盖分类编辑/启停、商品创建/编辑/上下架、价格/所属分类变更、套餐数量及成员集合保存。
- 所有目录写事务先取得 `store_settings(id=1) FOR UPDATE`，再按 ID 升序处理必要的既有商品；完整套餐定义和关联同事务提交，任一失败全部回滚。
- 新单或目录写未取得预置控制行时整体回滚并返回通用 HTTP `500`，不得无锁继续；此异常不使用环境/支付模式准入的 `50301`。
- 下单先获共享锁则按完整旧配置完成；编辑先获独占锁则新单等待并读取提交后的完整新配置。先点击或事务开始时间不决定配置版本。
- 不能先锁商品再请求控制锁，不能先共享再升级；目录编辑不得反向锁旧订单，锁内不能等待人工输入或外部服务。
- 取配置锁不改变营业开关、公告或营业变更时间。库存 delta、支付/取号、取消恢复及制作取餐保持既有协议，不反向获取控制锁。
- 历史订单仍使用原快照，不因目录变更重算金额或库存恢复；无须新增配置版本表。完整协议见 [系统架构](architecture.md) 和 [V1.0 业务与运行边界规则](v1-operation-rules.md)。

## 4. 库存需求

V1.0 采用轻量库存模型：

- `products.stock` 表示当前可售库存。
- 下单成功时原子扣减库存。
- 待支付订单取消或超时后恢复库存。
- 支付成功后不再次扣减库存。

核心 SQL：

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :product_id
  AND product_type = 'single'
  AND is_active = TRUE
  AND stock >= :quantity;
```

`:quantity` 为服务端汇总后的正整数实际需求，通过受影响行数判断是否完成扣减。有效商品库存不足时返回库存不足；已停用、类型错误或不存在的商品按商品校验错误处理，不能将所有 0 行结果都误报为库存不足。

### 4.1 并发规则

假设库存为 1：

用户 A 和 B 同时下单。

最终：

- 一方原子更新影响 1 行，成功。
- 另一方影响 0 行，业务层返回库存不足。
- 不允许两方都成功。

“谁先付款”不是库存竞争的判断依据；V1.0 的库存竞争发生在下单阶段。

### 4.2 库存取消释放

待支付订单取消/超时：

```text
订单 pending_payment
↓
cancelled
↓
恢复对应商品库存
```

释放库存、订单取消和支付记录置为 `closed` 必须放在同一个事务中。恢复数量来自原订单明细的 `stock_deductions`，不能根据当前套餐配置重新计算；商品后来停用也不影响原量恢复。

### 4.3 超时回收

- V1.0 必须自动回收待支付订单。默认 `PAYMENT_TIMEOUT_SECONDS=900`（15 分钟），创建时将截止时间固化为 `expires_at`；之后修改配置不改变既有订单期限。
- 独立轻量回收 worker 默认每 `ORDER_EXPIRY_SCAN_INTERVAL_SECONDS=30` 秒扫描一次，worker 启动时补扫；逐单事务关闭，失败可重试，多实例重复处理不会重复释放库存。
- 获取订单和支付记录锁后，使用数据库实际当前时间判断：`clock_timestamp() >= expires_at` 即到期。不能使用固定在事务开始时刻的时间判断等待锁后的期限。
- 支付入口也检查到期；扫描延迟不延长可支付时限。到期时先提交关闭及库存恢复，再返回 HTTP `409`、业务码 `40904`。
- 手动取消未到期订单记录 `cancel_reason=manual`；到期后执行取消或回收均记录 `timeout`。重复取消保留首次原因。
- 订单页提供继续支付、取消和到期提示，倒计时仅用于展示，服务端是期限及状态的最终依据。

## 5. 订单需求

订单状态：

```text
pending_payment
paid
making
ready
completed
cancelled
```

正常流程：

```text
pending_payment
      ↓
     paid
      ↓
    making
      ↓
    ready
      ↓
  completed
```

取消主要发生在：

```text
pending_payment → cancelled
```

禁止非法状态跳转，例如：

- completed → pending_payment
- cancelled → paid
- completed → making

状态变更必须由后端统一校验。

### 5.1 并发与重复操作

支付、取消及超时关闭统一在事务中按“订单 → 支付记录 → 所需商品按 ID 升序”的顺序获取锁，并在锁后重新检查状态。支付成功与取消释放库存不能同时生效。

- 已支付、制作中、待取餐或已完成订单重复支付：返回当前成功结果，不重复写入支付时间或流水。
- 已取消订单重复取消：返回当前取消结果，不再次恢复库存、不改取消原因。
- 已取消订单支付、已支付订单取消及其他非法跳转：返回 HTTP `409`。
- 合法组合及每种操作的事务边界详见 [订单状态机](order-state-machine.md)。

## 6. 支付需求

V1.0 使用 Mock 支付，仅由后端模拟结果以验证订单流程，不调用真实收款能力、不扣款、不实际收款。更换为 uni-app 客户端不改变该范围，也不表示其他平台支付已适配。

流程：

```text
提交订单
↓
pending_payment
↓
模拟支付
↓
payment.success
↓
订单 paid
```

支付状态：

- `pending`
- `success`
- `failed`
- `closed`

`refunded` 仅为未来退款设计预留，V1.0 不产生该状态。

订单状态和支付状态必须分开。

| 订单状态 | 支付状态 | 含义 |
|---|---|---|
| pending_payment | pending / failed | 等待首次支付或失败后重试，仍占用库存 |
| paid / making / ready / completed | success | 已支付，不再次扣库存 |
| cancelled | closed | 已关闭，库存已恢复 |

Mock 默认成功，确认失败由服务端测试配置模拟，客户端不得提交支付结果或失败开关。确认失败将同一条支付记录改为 `failed`，订单保持待支付、截止时间不变、库存不恢复；到期前可重试或手动取消。`payments.order_id` 保持唯一，失败重试不新建支付记录。

网络超时表示结果未知，应先查询订单；数据库异常则回滚事务，不等同于确认支付失败。确认失败状态必须提交后才返回 HTTP `409`、业务码 `40905`，不能因为抛出错误而回滚已确认的失败记录。成功后重复调用返回 HTTP `200`，不覆盖首次 `paid_at` 和 `transaction_id`。

V1.0 不接真实微信支付，但架构保留 `payment_method=wechat` 的扩展空间。

真实支付上线前需要重新设计支付回调、幂等、退款和商户资质等流程。

### 6.1 Mock 运行与营业隔离

- V1.0 的 `payment_method` 均为 `mock`，`success` 只表示模拟确认，不是已收款证明。取餐号及 `paid → making → ready → completed` 用于完整流程验收，不能进入真实制作和实物交付队列。
- 顾客与管理端必须在全局、支付、订单、取餐号及管理队列显著展示“模拟测试／未实际收款／不制作交付”；模拟制作、完成及确认取餐按钮采用对应测试文案，不能只有文档声明。
- 测试环境、数据库、库存、账号与未来营业环境隔离。V1.0 只上传并发布给受控体验测试人员，不公开接单营业。
- `APP_ENV` 必须显式为 `development/test/staging/production` 之一，`PAYMENT_MODE` 必填且 V1.0 仅实现 `mock`。缺失/未知配置或 `production + mock` 均拒绝启动，不能设置未实现的 `wechat` 模式绕过。
- 如运行中发现环境/模式不允许模拟操作，业务入口返回 HTTP 503、业务码 `50301` 并阻止副作用；API 与 worker 使用一致配置，不由前端决定。
- 空测试名单只拒绝顾客登录和受保护调用，不阻止合法测试环境中的管理员与 worker 清理遗留测试订单。既有鉴权、归属校验仍生效。
- 关闭 Mock 失败注入只让测试支付默认成功；暂停/恢复接单、生成取餐号均不改变测试属性。正式营业另设准入：可信实际收款、支付异常处理、测试/真实履约隔离和完整验收，V1.0 不提供营业解锁开关。

## 7. 订单快照

订单明细必须保存：

- 商品 ID
- 商品名称快照
- 单价快照
- 数量
- 小计
- 商品类型
- 套餐选择快照：子商品 ID、名称和每份数量
- 实际库存扣减快照 `stock_deductions`：该行消耗的普通商品 ID 和总数量；单品行同样保存

商品后来改名或涨价，不影响历史订单。

所有快照均由后端生成，客户端不得提交或覆盖。明细快照与订单、支付和库存变动同时提交；下单后调整套餐可选商品或每份数量，不改变历史展示及取消时的恢复量。

## 8. 管理端需求

管理员可以：

- 登录
- 查看分类
- 新增/编辑分类
- 启用/停用分类
- 新增/编辑商品
- 上下架商品
- 增加或减少可售库存
- 配置套餐
- 查看订单
- 更新订单状态（含 ready 待取餐、completed 已取餐）
- 暂停/恢复接单
- 查看基础数据概览

商品删除采用软删除/停用，不直接物理删除历史业务数据。

### 8.1 分类、商品与套餐完整保存

- 分类使用 `POST /api/v1/admin/categories` 和 `PUT /api/v1/admin/categories/{id}`，完整提交 `name`、`sort_order`、`is_active`；编辑同时覆盖启停。
- 套餐复用商品创建/编辑接口，完整商品定义包含所属分类、名称、描述、图片、价格、类型、排序、启用标记、`combo_quantity` 和 `allowed_product_ids`。PUT 为完整替换定义，不猜测未传字段或保留旧套餐成员。
- 普通商品 `combo_quantity=null`、`allowed_product_ids=[]`；套餐数量为正整数，允许商品集合非空且不得重复，只引用存在的普通商品。类型创建后不可变，套餐库存为 0，库存不得通过商品定义接口传入或覆盖。
- 套餐配置可以保留停用普通商品关联供管理维护，但顾客不能选择无效成员；不存在、嵌套套餐等非法引用全部拒绝。无有效选项或所选商品库存不足时不能创建订单。
- 分类停用不改写下属商品的自身启用标记，但统一阻止相关商品/套餐成员被新单购买。已创建订单的支付、制作、取餐及按快照恢复不受当前分类或商品停用影响。
- 元数据、价格、套餐数量及 `combo_products` 成员一次提交，任一失败保持全部原配置。结构缺失/禁止字段等返回 422；业务配置无效返回 `40001`；编辑目标不存在返回 `40401`。完整请求和响应见 [API 设计](api-design.md)。

### 8.2 库存调整

- 普通商品初始可售库存为 0，首次补货及后续修正统一走调整入口；套餐不允许独立调整库存。
- 管理员提交非零整数 `delta`、必填原因 `reason` 和独立 UUID `adjustment_request_id`；操作者来自认证上下文。
- `delta > 0` 增加可售库存，`delta < 0` 减少可售库存；数据库原子操作保证调整后不小于 0。
- 不提供实物盘点数量直接覆盖可售库存的操作；通用商品编辑接口不能修改已有 `stock`。
- 商品创建后不能修改 `product_type`，避免历史扣减快照引用的普通商品被改成套餐；名称、价格和套餐配方仍按既有管理功能维护。
- `stock_adjustments` 记录请求标识、内容指纹、商品、增减量、前后可售量、原因、操作者和时间，与库存变更同事务提交。
- 按 `(admin_user_id, adjustment_request_id)` 唯一去重；同键同内容重试返回原调整结果，不再次增减，同键不同内容返回 HTTP `409`。

### 8.3 管理端登录与身份隔离

- 管理 SPA 使用独立管理员登录流程及 JWT Bearer Token；顾客 Token 不能调用管理 API，管理员 Token 也不替代顾客身份。
- 管理员 Token 默认有效期为 8 小时，对应 `ADMIN_TOKEN_TTL_SECONDS=28800`。管理 API 校验签名、有效期、`actor=admin`、`aud=admin` 及管理员当前启用状态。
- 管理 SPA 将 Token 保存于当前标签页的 `sessionStorage`，请求携带 `Authorization: Bearer <token>`；不将 Token 写入 URL 或源码。
- 收到 `401` 或用户主动退出时，清理本地管理员 Token 和登录状态，进入 SPA 的管理员登录页面；重新登录后才能继续管理操作。
- 页面路径 `/admin/*` 由管理 SPA 处理，管理数据接口统一为 `/api/v1/admin/*`。隐藏页面或按钮不能替代后端管理员身份校验。

管理员登录接口及响应、页面路由和具体认证实现以 [API 设计](api-design.md) 和 [系统架构](architecture.md) 为准。

## 9. 安全需求

- `.env` 不提交 Git。
- Token 不写死在代码中。
- 后端验证所有价格、库存、商品状态。
- 顾客只能查看自己的订单。
- 管理端接口需要独立管理员身份，校验管理员 Token 的角色、受众和当前启用状态；顾客与管理员 Token 不得互用。
- 不允许前端直接决定订单状态。
- 不允许前端直接决定支付结果。
- 所有输入进行参数校验。

## 10. 非功能需求

### 正确性

重点保证订单、库存、支付的一致性。

### 并发安全

重点测试最后库存的并发购买。

同时覆盖同一次创建的并发重放、支付与取消/到期竞争、套餐与单品共享库存、库存调整与下单/取消竞争。测试清单及预期结果见 [测试计划](testing-plan.md)。

目录编辑和新单并发时必须得到完整旧配置或完整新配置，不能产生旧成员资格搭配新价格等不存在的定义；还需验证配置写失败全部回滚、分类停用竞争、同日取号唯一及模拟订单不进入真实履约。

### 可维护性

业务逻辑不能全部堆在 API 路由中，应拆分 service/repository 等层次。

同仓库分别维护 `backend`（FastAPI JSON API）、`admin-web`（Vue 3 + TypeScript + Vite + Element Plus）与 `customer-app`（uni-app + Vue 3 + TypeScript）。两类前端通过明确的 JSON API 契约访问业务后端，不依赖后端模板渲染管理页面；原有订单幂等、库存、状态机、超时、快照和失败重试规则保持不变。

### 可观测性

记录请求、异常、订单和支付关键日志。

### 可部署性

V1.0 使用隔离的开发、测试及 staging 环境，体验端使用 HTTPS；未来营业环境需另行通过支付与履约准入。

后端、管理 SPA 和微信小程序分别构建、分别部署或上传体验版。V1.0 staging 使用同域 Nginx 为 `/admin/*` 提供管理前端并将 `/api/v1/*` 转发给后端；前后端分离不要求跨域部署。微信小程序需单独完成目标平台的受控运行验收，不能以“uni-app 可编译”代替登录与业务流程的实测。

## 11. V1.0 摊位自取与接单要求

- 单摊位自取；首次 Mock 支付成功后按 Asia/Shanghai 经营日从 A001 起分配取餐号，失败、待支付和取消不占号。
- 管理订单按 `paid → making → ready → completed` 验证模拟待制作、制作中、待取餐、已取餐，不能跳级；整个 V1.0 流程不代表实际收款或商品交付。
- 暂停接单只拒绝新订单；商品浏览、旧单重放、旧单支付/取消、超时回收及制作取餐正常继续。
- 首次下单占幂等键后锁定单例营业配置 `FOR SHARE`，暂停时回滚并返回 40906；目录编辑使用同一控制行独占锁。完整规则见 [V1.0 业务与运行边界规则](v1-operation-rules.md)。
