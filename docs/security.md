# 安全设计

## 1. 身份认证

顾客：

```text
uni.login({ provider: 'weixin' })
↓ 微信目标登录适配
微信登录能力
↓
code
↓
后端换取 openid
↓
应用 Token
```

客户端后续使用：

```http
Authorization: Bearer <token>
```

顾客端为 uni-app + Vue 3，V1.0 仅支持微信目标的 code 换 openid 流程；框架其他编译目标不自动获得可用的登录服务。平台请求、存储和生命周期由客户端适配层封装，身份真实性仍由后端验证。

不允许：

```http
/orders/my?openid=xxx
```

作为身份认证方式。

## 2. Token

Token 应具有有效期。

Token 失效返回：

```http
401 Unauthorized
```

小程序重新登录获取 Token。

Token 不写入代码仓库。

## 3. 用户数据隔离

查询订单时：

```text
当前用户 ID
+
订单 ID
```

必须同时匹配。

支付、取消及订单幂等重放同样先验证当前用户身份和订单归属。`client_request_id` 只用于请求去重，不是访问订单的凭据；其唯一范围为 `(user_id, client_request_id)`，不能仅凭请求 UUID 查询其他顾客订单。

## 4. 管理员

管理接口必须验证管理员身份。

普通顾客 Token 不能访问管理 API。

管理端是独立 Vue Web 应用，页面位于 `/admin/`，管理 JSON 接口位于 `/api/v1/admin/`。管理员通过 `POST /api/v1/admin/auth/login` 以 JSON 提交账号密码；服务端校验密码哈希和启用状态后签发管理员 JWT。

- 默认有效期 `ADMIN_TOKEN_TTL_SECONDS=28800`（8 小时），返回 `expires_in`；JWT 必须验证签名、`exp`、`actor=admin`、`aud=admin` 及当前管理员启用状态。
- 管理员主体从经验证的 `sub` 取得，不能把顾客主体中相同的数字 ID 当作管理员 ID；前端路由守卫只控制界面，不能替代 API 权限检查。
- 管理端 Token 保存于 `sessionStorage`，附加到 Bearer 请求头；退出或 401 时清除本地认证状态。403 显示无权限，不把顾客 Token 换成管理员身份。
- 本地退出不等于服务端吊销已签发 JWT；V1.0 通过短期有效期及管理员启用状态检查控制后续访问，不引入额外会话表。
- 登录凭据和 Token 不进入 URL、业务日志或构建产物；认证错误返回 JSON，不返回 HTML 登录页或重定向。

库存调整操作者从管理员认证上下文取得，不能接受客户端指定 `admin_user_id`。调整请求标识按 `(admin_user_id, adjustment_request_id)` 唯一，重放仍须验证当前管理员身份。

## 5. 价格安全

前端传递的价格不可信。

服务器：

```text
product_id
↓
数据库读取价格
↓
Decimal 计算
```

该规则用于首次成功创建订单。已创建订单的幂等重放读取原金额快照，不按现价重新计算；`request_hash` 由服务端对规范化业务内容计算，不能信任客户端指纹，也不将当前价格加入指纹。

## 6. 库存安全

库存不接受前端直接设置。

普通下单：

```text
数据库原子 UPDATE
```

管理端修改库存：

```text
管理员权限
+
服务端校验
```

- 仅普通商品允许调整；请求为独立 `adjustment_request_id`、非零整数 `delta` 和必填原因 `reason`。
- 普通商品初始库存为 0，首次补货也走调整接口；通用商品编辑不得覆盖已有 `stock`。
- 原子校验 `stock + delta >= 0`，与 `stock_adjustments` 记录同事务提交，记录操作者及前后数量。
- 重试复用同一调整标识与内容，只返回原结果；同键异内容拒绝，不能依赖前端禁用按钮去重。
- 服务端生成订单 `stock_deductions`，不接受客户端传入的扣减或恢复快照。恢复必须与订单关闭同事务，且只允许第一次关闭生效。
- 商品停用不阻止旧订单按快照恢复；快照中引用的商品不物理删除。

## 7. 支付安全

Mock 支付阶段：

- 支付结果由后端决定。
- 客户端不能直接把订单改成 paid。
- Mock 默认成功，失败场景通过服务端测试配置注入；支付请求不得包含自选成功/失败结果。
- 只允许未到期的待支付订单在 `payment=pending/failed` 时发起新的支付尝试，失败保留原单并允许期限内重试。
- 支付、取消、超时关闭统一锁订单及支付记录，锁后判断状态和实际当前时间；客户端倒计时或设备时钟不能决定是否到期。
- 已成功请求重放不覆盖首次流水和支付时间；已关闭订单不能恢复为已支付。取消和到期使用 `payment.closed`，V1.0 不产生 `refunded`。
- 网络超时不能由客户端转换为失败或取消；先查询服务端结果，再决定允许的下一步操作。

未来接真实微信支付：

- 必须验证支付回调。
- 必须考虑回调重复。
- 必须保证支付处理幂等。
- 必须考虑退款。

## 8. 配置安全

`.env`：

```text
不提交 Git
```

`.env.example`：

```text
只保留变量名和示例值
```

敏感信息：

- 数据库密码
- Token 密钥
- 微信 AppSecret
- 真实支付密钥

均不能写入代码仓库。

前后端配置分别管理：后端 `.env` 保存数据库和微信/JWT 密钥；前端环境变量会进入公开构建产物，只允许配置 API 地址等非秘密值，不能因为变量写在 `.env` 中就认为前端值保密。

### 8.1 API 代理与浏览器跨域

- 生产优先同域 Nginx 分流 `/admin/` 静态页面及 `/api/v1/` 后端 API，SPA 页面回退不能吞掉 API 的 JSON 错误。
- 开发优先 Vite API 代理；需要浏览器跨域时只允许环境配置中的明确 Origin、实际方法及 Authorization/Content-Type 请求头。
- Bearer 管理请求不依赖 Cookie；不启用跨域 Cookie 凭证，不允许任意 Origin 代替来源白名单。CORS 不替代鉴权。
- 微信小程序按平台要求配置合法 HTTPS 请求域名；此规则与浏览器 Origin 检查分别验收。

## 9. 输入校验

所有 API 使用 Pydantic 校验：

- 类型
- 长度
- 数量
- 金额
- ID

数据库层继续使用 CHECK/UNIQUE/FK 等约束。

六项规则涉及的校验至少包括：

- 请求 UUID 格式、非空订单项、商品数量正整数；拒绝将小数或布尔值当作数量。
- 套餐每份选择数量合计正确、子商品 ID 不重复且属于允许的普通商品；普通商品不接受套餐配方。
- 库存调整 `delta` 为非零整数，`reason` 为 1 至 500 个字符且不能全为空白；不接受客户端库存绝对值。
- 请求中不能覆盖服务端生成的用户、操作者、快照、指纹、支付结果或截止时间字段。
- 持久层的请求唯一约束与应用层规范化一起使用；订单及调整请求的完整规则见 [API 设计](api-design.md)。

## 10. 日志

日志不能记录：

- AppSecret
- Token
- 密码
- 支付密钥

关键业务日志使用订单号等非敏感标识进行关联。

## 11. V1.0 自取与接单安全

取餐号不作为订单访问凭据；顾客仍只能查本人订单。只有管理员可以更新接单状态，后端新单事务内校验，不信任 UI 禁用。编号在支付成功事务中生成，客户端不能指定取餐号、ready 或 completed。详见 [V1.0 自取与暂停接单规则](v1-operation-rules.md)。
