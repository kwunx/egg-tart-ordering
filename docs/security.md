# 安全设计

## 1. 身份认证

顾客：

```text
uni.login({ provider: 'weixin' })
↓ 微信目标登录适配
微信登录能力
↓
code
↓
后端换取 openid
↓
应用 Token
```

客户端后续使用：

```http
Authorization: Bearer <token>
```

顾客端为 uni-app + Vue 3，V1.0 仅支持微信目标的 code 换 openid 流程；框架其他编译目标不自动获得可用的登录服务。平台请求、存储和生命周期由客户端适配层封装，身份真实性仍由后端验证。

V1.0 采用服务端 `MOCK_ALLOWED_OPENIDS` 测试身份名单：以逗号分隔，去除各项两端空白、去重后精确匹配微信服务返回的 openid。空集合默认不允许顾客登录；合法但未授权测试身份返回 HTTP 403、业务码 `40301`。不得接受前端传入的 openid、名单、测试开关或管理员 Token 代替顾客登录。

签发顾客 Token 前以及每次受保护顾客请求都要重新检查名单，已有 Token 不豁免；移出名单后不能继续用旧 Token 操作。公开商品和摊位状态仍可查询，这不授权下单或支付。空名单不阻止合法测试环境中的管理员及 worker 运行。

不允许：

```http
/orders/my?openid=xxx
```

作为身份认证方式。

## 2. Token

Token 应具有有效期。

Token 失效返回：

```http
401 Unauthorized
```

小程序重新登录获取 Token。

Token 不写入代码仓库。

## 3. 用户数据隔离

查询订单时：

```text
当前用户 ID
+
订单 ID
```

必须同时匹配。

支付、取消及订单幂等重放同样先验证当前用户身份和订单归属。`client_request_id` 只用于请求去重，不是访问订单的凭据；其唯一范围为 `(user_id, client_request_id)`，不能仅凭请求 UUID 查询其他顾客订单。

## 4. 管理员

管理接口必须验证管理员身份。

普通顾客 Token 不能访问管理 API。

管理端是独立 Vue Web 应用，页面位于 `/admin/`，管理 JSON 接口位于 `/api/v1/admin/`。管理员通过 `POST /api/v1/admin/auth/login` 以 JSON 提交账号密码；服务端校验密码哈希和启用状态后签发管理员 JWT。

- 默认有效期 `ADMIN_TOKEN_TTL_SECONDS=28800`（8 小时），返回 `expires_in`；JWT 必须验证签名、`exp`、`actor=admin`、`aud=admin` 及当前管理员启用状态。
- 管理员主体从经验证的 `sub` 取得，不能把顾客主体中相同的数字 ID 当作管理员 ID；前端路由守卫只控制界面，不能替代 API 权限检查。
- 管理端 Token 保存于 `sessionStorage`，附加到 Bearer 请求头；退出或 401 时清除本地认证状态。403 显示无权限，不把顾客 Token 换成管理员身份。
- 本地退出不等于服务端吊销已签发 JWT；V1.0 通过短期有效期及管理员启用状态检查控制后续访问，不引入额外会话表。
- 登录凭据和 Token 不进入 URL、业务日志或构建产物；认证错误返回 JSON，不返回 HTML 登录页或重定向。

库存调整操作者从管理员认证上下文取得，不能接受客户端指定 `admin_user_id`。调整请求标识按 `(admin_user_id, adjustment_request_id)` 唯一，重放仍须验证当前管理员身份。

## 5. 价格安全

前端传递的价格不可信。

服务器：

```text
product_id
↓
数据库读取价格
↓
Decimal 计算
```

该规则用于首次成功创建订单。已创建订单的幂等重放读取原金额快照，不按现价重新计算；`request_hash` 由服务端对规范化业务内容计算，不能信任客户端指纹，也不将当前价格加入指纹。

价格必须与同一套有效分类、套餐数量和成员配置一起确认。所有在线目录写入口先对 `store_settings(id=1)` 直接取 `FOR UPDATE`，新单取 `FOR SHARE` 后再读完整目录并保持到提交；双方均在控制锁之后按 ID 升序处理必要商品，不能反向取锁或共享锁升级。只给库存 UPDATE 加锁不足以保护多次配置读取。目录保存不能改营业字段；完整规则见 [V1.0 业务与运行边界规则](v1-operation-rules.md)。

新单或目录写未取得预置控制行时整体回滚并返回通用 HTTP `500`，不得降级为无锁执行；`50301` 仅表示环境/支付模式不允许模拟操作。

## 6. 库存安全

库存不接受前端直接设置。

普通下单：

```text
数据库原子 UPDATE
```

管理端修改库存：

```text
管理员权限
+
服务端校验
```

- 仅普通商品允许调整；请求为独立 `adjustment_request_id`、非零整数 `delta` 和必填原因 `reason`。
- 普通商品初始库存为 0，首次补货也走调整接口；通用商品编辑不得覆盖已有 `stock`。
- 原子校验 `stock + delta >= 0`，与 `stock_adjustments` 记录同事务提交，记录操作者及前后数量。
- 重试复用同一调整标识与内容，只返回原结果；同键异内容拒绝，不能依赖前端禁用按钮去重。
- 服务端生成订单 `stock_deductions`，不接受客户端传入的扣减或恢复快照。恢复必须与订单关闭同事务，且只允许第一次关闭生效。
- 商品停用不阻止旧订单按快照恢复；快照中引用的商品不物理删除。

## 7. 支付安全

Mock 支付阶段：

- 支付结果由后端决定。
- 客户端不能直接把订单改成 paid。
- Mock 默认成功，失败场景通过服务端测试配置注入；支付请求不得包含自选成功/失败结果。
- 只允许未到期的待支付订单在 `payment=pending/failed` 时发起新的支付尝试，失败保留原单并允许期限内重试。
- 支付、取消、超时关闭统一锁订单及支付记录，锁后判断状态和实际当前时间；客户端倒计时或设备时钟不能决定是否到期。
- 已成功请求重放不覆盖首次流水和支付时间；已关闭订单不能恢复为已支付。取消和到期使用 `payment.closed`，V1.0 不产生 `refunded`。
- 网络超时不能由客户端转换为失败或取消；先查询服务端结果，再决定允许的下一步操作。
- `payment_method=mock` 的 success 不构成收款凭据；制作、ready、completed 及取餐号在 V1.0 仅供模拟验收，不得用于真实实物交付。
- 客户和管理界面均必须展示模拟测试标识；任何前端开关、取消失败注入、恢复接单都不能将 Mock 切成正式收款或真实履约。

未来接真实微信支付：

- 必须验证支付回调。
- 必须考虑回调重复。
- 必须保证支付处理幂等。
- 必须考虑退款。

## 8. 配置安全

`.env`：

```text
不提交 Git
```

`.env.example`：

```text
只保留变量名和示例值
```

敏感信息：

- 数据库密码
- Token 密钥
- 微信 AppSecret
- 真实支付密钥

均不能写入代码仓库。

前后端配置分别管理：后端 `.env` 保存数据库和微信/JWT 密钥；前端环境变量会进入公开构建产物，只允许配置 API 地址等非秘密值，不能因为变量写在 `.env` 中就认为前端值保密。

### 8.1 Mock 环境准入

- `APP_ENV` 必填，仅接受 `development/test/staging/production`；`PAYMENT_MODE` 必填，V1.0 仅支持 `mock`。缺失或未知值启动失败，不能默认成允许接单的环境。
- `production + mock` 必须启动失败，未实现的 `wechat` 等模式同样拒绝；API 与 worker 均执行校验，修改变量名称或跳过前端提示不能解锁营业。
- 运行中若检测到环境/模式不允许模拟操作，业务入口在副作用前返回 HTTP 503、业务码 `50301`；不能以模拟成功继续创建或支付。已提交的历史结果不因此被删除，结果未知请求仍保留原标识待恢复。
- 测试数据库、库存、账号和履约环境与未来营业隔离；V1.0 只进行受控体验发布，不公开接单、不制作交付实物。全局、订单、支付和取餐号显著显示“模拟测试／未实际收款”。
- `MOCK_ALLOWED_OPENIDS` 由后端环境维护，不进入前端，不替代正常微信认证；仅在允许的测试环境中生效，不能用名单允许 production 运行 Mock。
- 未来营业单独验收真实收款确认、异常支付处理及测试订单/真实履约隔离。V1.0 无营业解锁开关，关闭 Mock 失败注入只改变模拟结果，不能解除运行准入。

### 8.2 API 代理与浏览器跨域

- V1.0 staging 使用同域 Nginx 分流 `/admin/` 静态页面及 `/api/v1/` 后端 API，SPA 页面回退不能吞掉 API 的 JSON 错误；路由可用于未来营业部署，但不是营业许可。
- 开发优先 Vite API 代理；需要浏览器跨域时只允许环境配置中的明确 Origin、实际方法及 Authorization/Content-Type 请求头。
- Bearer 管理请求不依赖 Cookie；不启用跨域 Cookie 凭证，不允许任意 Origin 代替来源白名单。CORS 不替代鉴权。
- 微信小程序按平台要求配置合法 HTTPS 请求域名；此规则与浏览器 Origin 检查分别验收。

## 9. 输入校验

所有 API 使用 Pydantic 校验：

- 类型
- 长度
- 数量
- 金额
- ID

数据库层继续使用 CHECK/UNIQUE/FK 等约束。

六项规则涉及的校验至少包括：

- 请求 UUID 格式、非空订单项、商品数量正整数；拒绝将小数或布尔值当作数量。
- 套餐每份选择数量合计正确、子商品 ID 不重复且属于允许的普通商品；普通商品不接受套餐配方。
- 库存调整 `delta` 为非零整数，`reason` 为 1 至 500 个字符且不能全为空白；不接受客户端库存绝对值。
- 请求中不能覆盖服务端生成的用户、操作者、快照、指纹、支付结果或截止时间字段。
- 持久层的请求唯一约束与应用层规范化一起使用；订单及调整请求的完整规则见 [API 设计](api-design.md)。

目录写接口单独校验完整定义：分类包含名称、排序和启用标记；商品包含类型及套餐字段，描述/图片可以显式为 NULL，但不能把缺少键解释为保留旧配置。禁止字段（含库存、ID、服务端时间）及结构错误返回 422。不存在的分类/套餐成员引用、错误类型等业务定义错误全部拒绝，不能部分写入。顾客商品查询、详情、套餐选项和下单统一要求相应商品与分类均启用，不能用查询参数读取停用数据；历史订单继续使用授权后的原快照。

## 10. 日志

日志不能记录：

- AppSecret
- Token
- 密码
- 支付密钥

关键业务日志使用订单号等非敏感标识进行关联。

## 11. V1.0 自取与接单安全

取餐号不作为订单访问凭据；顾客仍只能查本人订单。只有管理员可以更新接单状态，后端新单事务内校验，不信任 UI 禁用。编号在模拟支付成功事务中生成，客户端不能指定取餐号、ready 或 completed。暂停不影响旧订单，不是隔离测试订单或解锁真实营业的机制；目录配置保存也不能修改接单开关。详见 [V1.0 业务与运行边界规则](v1-operation-rules.md)。
