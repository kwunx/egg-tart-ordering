# 微信小程序点餐系统 - UI/UX 设计

## 1. 设计目标

- 简单
- 清晰
- 商品优先
- 操作路径短
- 套餐选择规则明确
- 购物车和订单金额明确
- 状态反馈明确
- 能映射到 uni-app + Vue 3 + TypeScript 的页面及组件，编译为微信小程序

顾客端位于 `customer-app/`，采用 uni-app CLI 的 `vite-ts` 工程，V1.0 仅交付和验收 `mp-weixin` 微信小程序。页面使用 uni-app 支持的组件和 API；WXML/WXSS 等由编译生成，无需手写原生页面。不在小程序中使用浏览器 DOM 或 Element Plus 管理端组件。框架具备多端编译能力，不代表 H5、App、支付宝或抖音的登录、支付和发布已经支持，这些目标属于后续范围。

管理端位于 `admin-web/`，采用 Vue 3、TypeScript、Vite、Vue Router、Pinia 和 Element Plus，作为独立 Web 应用构建。管理页面使用 `/admin/`，通过 `/api/v1/admin/*` 的 JSON API 与 FastAPI 通信，后端不返回管理页面模板或 HTML 片段。

### P03 套餐选择

显示每份套餐要求的总数量、当前每份选择数量和购买份数。`quantity` 表示套餐份数，`selections` 表示每份配方；每个子商品只显示一项数量操作，不能提交重复的子商品 ID。

必须覆盖：

- 0/6
- 4/6
- 5/6
- 6/6
- >6
- 库存不足

每份达到 6/6 且购买份数为正整数时可加入购物车。例如原味、芝士、芋泥每份各 2 个，购买 2 份时，实际需要各 4 个。库存提示按购买份数计算，最终是否可售以后端下单校验为准。

### P04 购物车

- 商品
- 数量
- 小计
- 删除
- 总金额
- 去结算

套餐行同时显示“每份口味配置”和“购买份数”。同商品、同配方合并数量，不同配方分行；配方比较不受子商品展示顺序影响。修改某一行配方不改变其他套餐行。

同一普通商品可能同时出现在单品行及多个套餐行，前端可汇总提示所需数量；后端仍会汇总全单实际消耗后统一检查库存。订单创建成功并取得订单号后才清理对应购物车项；请求结果未知时保留购物车和原始提交内容。

### P05 确认订单

- 商品快照展示
- 数量
- 金额
- 备注
- 总金额
- 提交订单

点击提交后显示处理中并禁用重复提交。提交意图使用持久化的 `client_request_id`，具体重试规则见第 4 节。该标识属于内部请求数据，不展示给顾客。

### P06 Mock 支付

- 待支付
- 支付按钮
- 支付处理中
- 服务器返回的订单总额
- 支付剩余时间
- 取消订单

创建订单及订单详情响应中，`data.expires_at` 是固定到期时间，`data.server_time` 是生成本次响应时的数据库当前时间；幂等重放返回新的 `server_time`，不改变原到期时间。初始剩余时间按 `max(0, expires_at - server_time)` 计算，随后按经过时长递减，不使用设备绝对时间计算截止。默认支付时限为创建后 15 分钟。

倒计时归零时暂时禁用支付按钮并查询订单；若同步后的服务器时间仍未到期且订单仍待支付，则重新校准倒计时并恢复按钮。已到期则保持支付不可用并等待服务器关闭结果；不能仅凭倒计时把订单改成已取消，也不能因设备时钟偏差永久禁用支付。页面返回前台、网络恢复和再次打开订单时均重新读取状态、`expires_at` 和 `server_time`，重新同步计时。

只有 `pending_payment` 且支付状态为 `pending` 或 `failed`、仍未到期的订单显示“继续支付”和“取消订单”。失败后继续支付沿用原订单；正常 Mock 支付默认成功，不提供让顾客选择成功/失败的控件。

### P07 支付结果

- 成功
- 失败
- 结果确认中

失败页面保留原订单入口：未到期时可重试或取消，已到期时提示重新下单。网络超时或响应丢失显示“支付结果确认中”，先查询原订单，不将网络错误直接显示为支付失败，也不重新创建订单。

成功页面以订单查询或支付接口确认的结果为准。已支付、制作中或已完成的原单再次返回时展示当前状态，不重复发起支付。

### P08 我的订单

显示当前用户订单。待支付订单提供继续支付和取消入口；已取消订单展示取消原因，区分“已取消”和“超时未支付，订单已取消”。从列表进入原单继续处理，不为未支付订单重新建单。

### P09 订单详情

显示：

- 订单号
- 商品
- 数量
- 套餐选择
- 金额
- 订单状态
- 支付状态
- 时间
- 待支付订单到期时间
- 取消原因（手动取消或支付超时）

套餐选择使用历史快照展示每份配方和份数，不随当前套餐配置变化。订单状态读取 `data.status`，支付状态统一读取 `data.payment.payment_status`，创建、详情、支付和取消响应保持该层级；不得读取顶层 `data.payment_status`。两种状态分别展示：`cancelled + closed` 表示订单和支付均已关闭，`pending_payment + failed` 表示本次模拟支付失败但原单仍可在到期前重试。

取消操作进入处理中状态并禁用重复点击；完成后按服务器结果刷新。取消请求超时则先查询原单，仍待支付时可以对原单重试取消。到期后的取消显示超时原因，即使操作来自顾客手动点击。

- 网络错误
- 请求失败
- 提交结果未知，正在恢复原订单
- 订单已过期
- 当前订单状态不允许操作
- 同一请求内容发生冲突

## 4. 关键交互

前端可以提前展示库存状态，但最终库存必须以后端结果为准。

例如：

```text
用户点击提交
↓
后端返回库存不足
↓
前端显示“库存不足，请重新选择”
```

不能因为前端显示“有库存”就认为下单一定成功。

### 顾客端平台适配与请求层

- 微信端使用 `uni.login({ provider: 'weixin' })` 获得 code，提交后端换取微信 openid 并签发应用 Token。框架调用不改变原有微信身份链路；顾客 Token 的具体方案仍在 Phase 4 决定。
- 统一封装 `uni.request`，使用环境配置的 API 绝对地址并附带 `Authorization: Bearer <token>`；同时检查 HTTP 状态和响应中的整数业务 `code`，不能把请求回调成功直接当作业务成功。
- 请求层区分服务端明确返回的业务失败与断网、超时、响应丢失造成的结果未知。写请求不得在结果未知时自动换 UUID；订单恢复、支付查询及错误提示继续遵循下列规则。
- 使用 uni-app 存储 API 按用户保存购物车、待恢复下单 UUID、完整提交内容和订单 ID。使用页面/应用生命周期在回到前台时同步订单状态及倒计时，网络恢复后同样同步；平台适配不能重置原请求标识或支付期限。

### 4.1 下单重试与本地恢复

1. 每次确认新的下单内容时生成 UUID 格式的 `client_request_id`，发请求前将当前用户、标识、完整提交内容及提交状态写入本地持久化存储。
2. 重复点击、网络超时、重新进入小程序以及登录 Token 更新后的重试，复用该标识和原始内容。等待结果期间锁定提交内容；结果未知时先恢复原单结果，再允许修改内容发起新的下单意图。
3. 新建订单收到 HTTP `201`；同一用户、同标识、同内容重试收到 HTTP `200` 和原订单当前状态，可能已支付或已取消。前端按该状态进入对应页面，不假定一定处于待支付。
4. 原单恢复成功后持久化订单 ID，并结束该次提交处理中状态。商品后来改价、下架或套餐改配方，不影响凭原标识恢复已创建订单。
5. 修改商品、数量、配方或备注后重新提交属于新内容，生成新 UUID；不能在原标识下替换请求内容。HTTP `409`、业务码 `40902` 表示幂等内容冲突，应停止自动重试并提示重新确认。
6. 本地待恢复记录按用户隔离；重新登录同一用户后继续恢复，切换用户不读取或重发他人的待恢复请求。不能在发请求后、确认创建结果前丢弃请求标识。

### 4.2 支付、取消与超时反馈

- 支付、取消互相禁用按钮，等待中的状态变更完成后再刷新可用操作；前端按钮控制不替代后端并发校验。
- 支付失败时保留原订单 ID，点击重试仍调用原订单的支付接口，不创建新订单或新支付记录。
- 支付结果未知时先查询订单；若已成功则显示当前订单状态，若仍待支付且未到期则允许在原单继续支付，若已取消则关闭支付入口。
- 业务码 `40904` 表示已过期。后端在返回该错误前已提交超时取消和库存释放，前端刷新后展示“超时未支付，订单已取消”。
- 业务码 `40903` 表示当前状态不允许操作，先刷新原单；`40905` 表示已确认的 Mock 支付失败，展示重试或取消入口。`40901` 表示库存不足，返回购物车调整内容。
- 手动取消与超时取消使用相同的关闭结果；再次打开已取消订单只能查看，重新购买必须重新确认商品、库存和金额并使用新的下单标识。

## 8. 管理端库存调整交互

本节只补充库存增减操作，其他管理端页面继续按现有功能范围实施。

- 普通商品的编辑页显示当前可售库存但不能直接覆盖库存；新建普通商品初始库存为 `0`，通过“调整库存”入口补货。套餐没有独立库存，也不提供库存调整入口。
- 调整表单显示商品、最新可售库存、增减数量、调整原因。数量为非零整数 `delta`：正数表示补货，负数表示减少；`reason` 为 1 至 500 字符且不能全为空白。页面显示预计调整后数量，最终数值以服务器结果为准。
- 例如“当前 10、增加 5、原因：新出炉”提交 `delta=5`；盘亏 2 个提交 `delta=-2` 并填写原因。预计为负时提示不能提交，后端仍独立校验并发后的库存不会为负。
- 确认提交前生成并持久化独立 UUID `adjustment_request_id` 和完整表单内容，按管理员隔离；处理中禁用重复提交。响应丢失或重新打开页面时，复用原标识和内容重试获取原调整结果，不能生成新标识再次加减。
- 同标识不同内容返回 `40902` 时停止重试并重新确认；变更增减量或原因属于新操作，使用新标识。结果未知时先恢复原调整结果，再允许创建下一次调整。
- 成功后展示调整前/后库存、增减量和原因，刷新当前库存；重试恢复的原调整结果不代表当前最新库存，应另行刷新。库存不足返回 `40901` 时保留表单内容并刷新库存供管理员重新判断。

## 9. 管理端登录与页面请求

- 登录页面为 `/admin/login`，提交 `POST /api/v1/admin/auth/login`。读取返回的管理员 JWT 及 `expires_in`；默认 `ADMIN_TOKEN_TTL_SECONDS=28800`，即 8 小时。
- 管理员 Token 存放于 `sessionStorage`，Pinia 管理当前会话状态；统一封装 `fetch` 发送 JSON，请求携带 `Authorization: Bearer <admin_token>`。商品、库存、订单操作均更新 Vue 页面状态，不使用服务端 HTML 片段替换。
- 收到 HTTP `401` 或主动退出时清除本地管理员 Token 及会话状态，进入 `/admin/login`；HTTP `403` 展示无权限，不当成登录成功或自动换用顾客身份。前端路由守卫不能替代后端权限检查，顾客 Token 无权访问管理 JSON API。
- 待恢复的库存调整标识及表单按管理员独立持久化，与 `sessionStorage` 中的 Token 分开；认证失效不删除结果未知的调整记录，同一管理员重新登录后恢复原请求，其他管理员不可读取或重发。
- 管理端以 `/admin/` 为路由和静态资源基础路径，直接打开、刷新 `/admin/orders` 等深链接应展示对应页面。API 错误继续按 JSON 处理，不能被 SPA 页面回退替换成 HTML。
- 本地开发通过 Vite 将 `/api/v1` 代理到 `http://127.0.0.1:8000`；生产环境由 Nginx 在同域提供 `/admin/` 静态文件并将 `/api/v1/` 反向代理到后端。微信小程序使用配置的 API 绝对地址和合法 HTTPS 域名，不依赖浏览器开发代理。前后端独立构建不要求跨域；未来 H5 或其他实际跨域场景才配置准确的来源白名单。
